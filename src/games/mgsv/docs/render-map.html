Render map

How Metal Gear Solid V draws a frame, which engine plugin records each part, and where RenoDX changes it.

The frame comes from five single-frame probe captures of the committed build, joined by job position. The ACC title screen ran with the preset on, so Bend contact shadows and diffuse GI ran there; its reflections took the native trace. An outdoor hillside, Mother Base at night, Mother Base in rain, and the sortie menu ran with the preset Off, which leaves only reconstruction and native-equivalent post-processing ports. All five reconstruct 1920 × 1080 to 3840 × 2160. The rain capture also builds a separate 512 × 512 rain occlusion view ahead of the main view. The plugin map comes from a static reading of the executable, and the probe's plugin marks confirm every owner at run time. Event IDs in the reference views come from the addon-off Mother Base frame 32052 at 3840 × 2160.

Evidence limits: this is one frame per scene, and node numbers and walk positions are local to each capture. Each stage and job names the plugin instances that record it, from the executable reading. The probe marks every plugin's entry and exit, so these owners are observed: a stage's owners are the plugins whose code recorded its draws, and a job's owners include the plugin that branched it. A job's own draws record on pool threads, which carry no plugin marks. Targets are listed as bound, with view formats; a target the engine names is shown by that name, and an RGBA16F view that replaced a game view says which (render targets and view formats). The ACC capture also includes RenoDX's capture attachments. D3D12 work is outside these D3D11 captures. The hillside has no ocean; the addon-off phase table shows a frame with no addon at all.

Frame start and rain occlusion view

Recorded by the root node: the frame-level clears, then the rain view's own clears. While rain falls and shelter volumes are near the camera, the rain filter's TextureDrawer adds this 512×512 viewport with its own scene and only plugin category 4 enabled, at a priority ahead of the main view. Category 4 is the three 2D plugins; DRAW2D_SHRINK is a child of POSTFILTER, which is category 3, so only DRAW2D and DRAW2D_FRONTMOST run here. The view's end-of-view copy into its 512×512 texture opens the next node, which then carries on as the main view's first stage.

The frame

Frame order in finer detail

The reference frame supplies the native ordering. The source adds shared indirect lighting before skin scattering and reconstruction before bloom preparation. Transparent effects occur in several groups.

  1. Scene inputs.

    Camera and scene size → fog preparation → opaque and masked surfaces → decals → object and camera motion → native AO and ambient lighting.

  2. Lighting, with RenoDX work.

    Local and directional lights with enhanced shadows → diffuse copy and source preparation → shared indirect lighting → both skin scatters → deferred composition and fog.

  3. Remaining scene.

    Visible sky and clouds → forward objects → native SSR → ocean and remaining particles, liquids, and rain → brightness measurements.

  4. Reconstruction and output, with RenoDX work.

    TAA, FSR, or DLSS → bloom → DoF → flare-layer composition → motion blur → grading and late tonemap → FXAA bypass or native FXAA → UI → display encoding.

The preferred reconstruction entry is immediately before the qualified CopyReductionX4 0x72C1D157 draw. In the job tree that is the cut in Exposure, bloom, and depth of field; in the reference frame it is before EID 47966. Bloom and DoF therefore use the reconstructed scene. Supported later entries provide recovery when that opportunity is absent.

MGSV applies early color treatment in some scene shaders as well as a late tonemap. Float scene storage can contain encoded RGB. Each replacement follows the producer and view conversion at its actual position. Color and ordering contracts Secondary views and utility jobs can have separate targets and recording schedules.

RenoDX adds no nodes. It replaces shaders inside native lists, records extra dispatches inside some of them, and cuts four native lists so its own work runs between the pieces.

What RenoDX changes

Lighting and reflection handoffs

Where RenoDX's lighting work attaches to the native passes, in frame order.

  1. Capture material meaning beside native geometry.

    Qualified opaque and wet-material replacements preserve the original outputs and add clean material color and exact surface ownership guides. Small readiness and composition masks are reset by native surface writes. Rain variants 0x2C230875 and 0xC3538951 have their own original two-target layout.

    Material capture · Qualified shader inventory

  2. Keep ambient diffuse separate from direct light.

    SSLighting2_SH_SkyLight_Encode 0x4FBDBB39 identifies the ambient family. BilateralUpscale2x2 0x844CE327 supplies small-grid ambient at pixel t0, depth at t2, phase weights at t3, sampler s8, and the original vertex/pixel b5 ranges. The later application reproduces this upsample to isolate the ambient contribution.

    Ambient capture · Full-resolution application

  3. Apply direct-light shadows inside the native light draws.

    PCSS filters native sun/moon, spot, and point shadow maps. Bend contacts read camera depth and the exact light and scene constants. Compatible unshadowed local-light groups share setup, clear, and trace dispatches in a packed atlas. Shadow-map jobs and unsupported groups use the per-light route. The spot contact budget defaults to 34.

    Contacts and soft map visibility affect direct diffuse and direct highlights. Native environment reflections, projected masks, fades, and alpha keep their separate roles. Local-light jitter is written once into the completed native packet before its workers inherit it.

    Shadow algorithm and coverage · Bend batching · Owned light-packet correction

  4. Prepare shared radiance in the existing diffuse copy.

    CopyBuffer 0xD71E843E reads original diffuse at t0 and material at t1. Target 0 retains the native diffuse and skin-mask alpha. Added inputs t18–t22 qualify albedo, normal, depth, clean color, and owner guides. Target 1 writes FP32 outgoing diffuse radiance for the diffuse AO/GI search. A valid black source still blocks light.

    Supported sun/environment draws separately capture environment RGB at target 2 and retain the matching palette at t10. The native shaders still use Fresnel at t9, but GGX does not capture it. Immutable palettes are reused. Mutable palettes are copied in their native command stream.

    Source preparation · Environment and table capture

  5. Trace and filter diffuse indirect light before skin scattering.

    The first scatter, compute 0x6DAF0C4A, supplies copied diffuse t0, depth t1, normals t2, and 64-byte geometry b0. After submitting the native prefix, one trace shares depth samples between diffuse AO and GI. Specular rays, cone integration, and specular histories are no longer part of this pass.

    One temporal pass shares geometry and reprojection setup while accepting AO and diffuse radiance independently. Three default A-Trous passes retain the center and sample one quarter of the neighbor pattern. The final full-resolution application makes six default dispatches in total. Coarse depth sampling adds four optional reductions.

    The default lighting grid contains one quarter of the render pixels, with each axis divided by two and rounded up. Search radius is expressed in output pixels. Lighting noise uses the scene-reserved jitter sample when reconstruction is enabled. Lighting maintains its own submitted history and replay rules.

    Full algorithm and signal rules · Input checks and scheduling · Trace · Temporal accumulation · Spatial filter

  6. Apply diffuse, scatter skin, then export the environment.

    Diffuse becomes direct + ambient × AO + diffuse GI. Missing ambient capture skips custom diffuse AO. With the feature enabled, the six supported deferred shaders bypass native diffuse AO even if custom dispatch fails, so that failure case currently has no diffuse AO.

    Both native skin-scattering passes still run once, with the original vertical bytecode for 0xB2601810. Deferred composition exports its exact environment term and receiver fog transmission to an extra RGBA16F attachment. CPU submission records retain its matching material and scene inputs for the later reflection stage.

    Reflection outputs and readiness · Registration and scatter callbacks

  7. Trace and compose at the native late reflection stage.

    Six supported deferred variants preserve direct highlights and export the replaceable environment, including qualified material-cube and wet-ground contributions. Pixel t16 supplies captured environment and t20 supplies clean material color. An added RGBA16F output carries the shaded environment and receiver fog transmission. RenoDX mode keeps lighting linear independently of the reflection toggle.

    Enhanced replaces general and sortie-floor native reflection traces with one GGX estimator. Preparation decodes the late extended-sRGB scene and writes NRD motion, world normal/roughness and view depth in the same dispatch. DX12 builds nearest-depth mips, traces the selected number of stratified GGX rays per input pixel (one by default) through screen light and unresolved environment, denoises their complete demodulated estimate with NRD REBLUR_SPECULAR, and restores material response. All stages share the existing device, queue, fences and one bridge handoff. The native compositor reads light at t18, diagnostic weights at t19, saved environment at t20 and readiness at t21, replacing environment once in linear light with receiver fog transmission. Cached replay does not advance history twice. Dependent native filters/copies are skipped; Vanilla restores native SSR. Missing inputs retain environment. NRD cannot recover hidden geometry or a directional sky from the integrated native fallback.

    Screen-light GGX and the game's integrated Blinn-Phong environment form the current approximation. Screen-visible source radiance still cannot supply hidden geometry or reevaluate directional lighting and fog along the reflected path. Wider material, off-screen, and directional transport work remains ahead.

Recording, submission, and GPU execution

The columns below describe dependencies. Workers can record overlapping scenes and effects. A finished command list retains its recorded commands until submission. GPU completion requires completion evidence. Column widths and list positions have no timing scale. The job tree lists one frame's command lists in submitted order, and its recording figure shows which thread recorded each.

Scene preparation

  1. The shared Dg renderer rebuilds scene resources when the native size plan changes.
  2. A native scene build publishes renderer, viewport, presentation, and generation identity.
  3. Main camera setup reserves jitter and saves the original matrices for that scene.
  4. Plugin branches and copied subcontexts carry that identity into worker jobs.

Parallel worker recording

  1. Lighting, scene effects, flares, and UI can record on different deferred contexts.
  2. Every routed draw selects the scene's retained output and exact resource roles.
  3. FinishCommandList transfers output references and ownership metadata to the native list.
  4. Display recording closes the open sequence. Late workers still find that scene's producer and clears.

Ordered submission and execution

  1. The native walk submits completed lists in tree order: a node, its child, then its next sibling.
  2. The coordinator preserves prefixes and remainders around custom immediate-context work.
  3. Successful reconstruction installs output, then commits its camera-history endpoint.
  4. Remaining post-processing, UI, and display work consume the retained output. GPU queries can establish completion.

A worker finishing display recording before a flare worker is a supported order. Earlier native clears move into the output producer when its allocation is acquired. The producer keeps them until reuse, allowing that late worker to initialize the enlarged flare layer. Startup scenes that never acquire output retire their pending clear records at display completion.

Output reuse waits for recording contexts, open sequences, and native command lists to release their references. Compatible spare allocations support concurrent scenes. A cached list replay preserves native work. Reconstruction uses the spatial fallback for that repeated observation, Bend recomputes contacts, and indirect lighting consumes its copy association once.

These rules come from the retail decompiles. The generator asserts the ones a capture can show: child and sibling placement, walk order, and that recording ends before the walk. Engine names such as CommandListNode::Branch come from a community symbol database for another build and are used only where the retail function's logic matches.

  1. Setup. Three node pools rotate. Setup advances to the next pool, resets it, and allocates the root node. A node is 32 bytes: next sibling, first child, list handle, and flags. Flag bit 0 means the node holds a finished list.
  2. Inline recording. The build thread records each plugin's own commands into the current node. BeginRecord clears the ready bit. EndRecord finishes the list and sets it.
  3. Branching. When work goes to a job, DgDx11::Branch ends the open recording and CommandListNode::Branch gives the job a new child, then inserts a continuation sibling after the current node. With no recording open, the job takes the continuation itself and Split inserts another. The first job after an inline list is therefore that node's child, and later jobs are siblings.
  4. Jobs. A job wraps its copied subcontext in a command buffer, records on its own deferred context, and can branch the same way. The shadowed-light job does this for every light. Eighteen threads recorded lists in each capture, including the thread that later ran the walk.
  5. Walk. After every list is finished, DgDx11::Kick walks from the root: submit the node's list if it is ready, walk its child, then move to its sibling. The walk ran on a pool thread, a different one in each capture. One list from a separate thread executes first; the probe saw no draw, dispatch, clear, or copy in it.
  6. Addon cuts. At an insertion point the coordinator finishes the native list early and queues its own work. At submission it executes that prefix, runs the immediate-context work, and lets the native remainder follow. A cut node therefore submits two or three lists.

Status

What is confirmed and what is open

Where the account of the frame stands after the probe captures and the reading of the executable. Each claim links to its evidence in the frame or the engine plugin explorer.

Confirmed by captures

  • One structure for every scene. The 14 inline stages, their job slots, and the plugin that owns each fit every capture without exceptions: two sets of five, taken before and after the experimental build was reverted.
  • Owners observed at run time. All 64 owned stages and jobs match the plugin marks in every capture. One correction came from them: POSTFILTER records nothing in stage 12; its PreExec only precedes its children there, and its work is in its last slot in stage 13.
  • Only three things change the shape of the tree. Terrain jobs repeat once per terrain object and are absent at Mother Base. The shadowed-lights job builds a group of nodes per light (0, 3, 4, 10, and 16 lights seen). Rain adds a view before the main one.
  • Native reflections. Stage 10 runs the full native chain in the four preset-Off captures and in the ACC, whose reflections took the native trace even with the preset on. The trace is generic everywhere except LocalReflectionTPP in the sortie menu.
  • Rain. The occlusion view, the wet G-buffer layer at the start of stage 2, the DR_TonemapRainFilter composition, and rain particles in the second primitives pass. An unpaused rain frame still draws the sun with SunLight_DL and SunLight_DL_CS, without environment specular, so the weather selects them. Object motion vectors record nothing in either Mother Base capture, rain or not.
  • View formats and sRGB. Every game sRGB view that RenoDX replaced with an FP16 copy converts in a FIX_UNORM_SRGB block, or cannot change its value. No engine texture is reached both through a copy and through its own 8-bit view. See render targets and view formats.
  • Ocean, night, and small effects. The Fourier ocean draws in the first primitives pass. Moon shadows use the four sun cascades. Stars and generative clouds are forward models. Skid marks draw in the raw-decal job, camera droplets in the half-resolution 2D job, and collectible thermography in its own job.
  • A near-native reference. With the preset Off only 36 shader uses (21 shaders) in the Mother Base frame were ports: late post-processing, the composition, and the sky. The single RenoDX cut left is reconstruction in stage 12.

Settled from the executable

  • Texture slot t10 in the deferred lighting plugins is the engine material texture, the second field of TextureManager::m_shaderTextures, loaded from a file by the Lua call GrTools.SetMaterialTexture. The first field is the default reflection texture and the third is the cloud shadow texture.
  • Viewport flag bit 18, which would skip deferred geometry, lights, and reflections, starts clear (the constructor sets 0x30070) and no readable code sets it. The skip is inactive in practice.
  • Plugin categories decide what a secondary view runs. The rain view enables only category 4, the three 2D plugins, and the half-resolution one is a child of the post-filter plugin (category 3), so the view runs exactly two jobs.
  • Render targets. Every target comes from a RenderTargetParameter whose format code maps to a typeless texture with separate render-target and shader views. Each of those views has its own sRGB flag, and an _SRGB name is a second entry sharing the plain entry's texture. The live table is ResourceManagerBase<RenderTargetResource> at 0x142B73428. Names are checked by StrCode64; the decomp database misnames one global (0x1429E6B30), and the G-buffer velocity passes write GBUFFER_MATERIAL.
  • Unused shaders. CopyReductionX2, LocalReflectionComposite, SSLighting2_Sun_LargestCascade, and the Tone composition variants are never bound in this build; the _1DLUT late passes are unreachable after the first color-correction run.

Still open

  • Who records a job's draws. The probe's hook on RenderPlugin::_Exec (0x1BED80) observes which plugin branches each job, but a job records on a pool thread with no plugin marks, so a second owner such as ALPHA_MODEL in the second primitives pass is still matched. Plugin order and parents are game data, so a patch or scene could reorder them.
  • Paths no capture has taken. Cutscene depth of field and the gather and near-only paths; tonemapping off (the ColorCorrection late pass); sandstorm and fog weather; the _MD and _NoIR composition variants; the TPPA1 and TPPA2 reflection traces; night-vision goggles; optical camouflage; the wormhole; the 24-hour ocean.
  • Other views. Only the rain view has been captured. Mirrors, the ocean-wave and water-ripple views, the avatar photo, and the cigarette hologram build their own views, and their order against the main view is unknown.
  • Post-processing at output size. With reconstruction active, bloom, Tonemap, and GammaControl run at the output size on RenoDX's own resources, so the captures do not show which game views those passes replace. A one-frame DevKit snapshot at native size covered that chain.
  • Unknown switches. The writers of the camera flags that gate tonemap, depth of field, and FXAA; the primitive flags that force the second pass; how the effects-quality index maps to the settings menu.
  • The list before the walk. One list from a separate thread executes first, followed at Mother Base by two immediate copies from 64 × 64 staging textures. Its recording has never fallen inside a capture.
  • Known only from the 2015 build. Retail obfuscates the sky precompute, post-filter setup, the tonemap enable, the custom composition material, and the alpha-model layer registration. About a fifth of the plugin claims carry a dev or inferred tag.
  • No fully addon-off tree. The preset Off still ports late post-processing. The addon-off RenderDoc frame in the reference views is the only capture with no addon at all, and it has no command tree.

To extend coverage, take a one-frame probe capture in the scene, add it to cases.json, and regenerate. A frame that breaks the stage and job table fails with the position.
