# AGENTS: MGSV contributions

Scope: `src/games/mgsv/**`. This file adds MGSV-specific rules to the [root guidance](../../../AGENTS.md) and [game-mod guidance](../AGENTS.md). General C++ style, helper design, dependencies, and change-scope rules are inherited, not repeated here. See [ARCHITECTURE.md](docs/ARCHITECTURE.md) for file ownership and known limitations, and the [reconstruction README](reconstruction/README.md) for temporal contracts and verification.

## Local conventions

- Use plain American English in comments, documentation, UI, logs, and proposed commit messages: `color`, `behavior`, `initialize`, and `organization`. Preserve external names, saved keys, quotations, and attribution.
- Keep each Markdown paragraph and list item on one source line. Do not introduce MGSV-specific formatter or lint overrides.
- Keep logs limited to useful changes, failures, and recovery; avoid per-frame success messages and repeated warning spam.
- Keep everything that knows the game executable under `engine/`: the table of addresses and structure fields (`engine/build.hpp`) and the engine hook points other features build on. Organize shared infrastructure under `rendering/`, material capture and native material ports under `materials/`, native lighting and direct shadows under `lighting/native/` and `lighting/shadows/`, diffuse tracing/filtering/application under `lighting/indirect/`, and stochastic reflection work under `lighting/reflections/`. Bloom belongs under `postprocess/bloom/`, the fog volume under `atmosphere/fog/`, and ports of particle shaders under `effects/particles/`. Keep the existing purpose-based `copy/`, `reconstruction/`, `tonemap/`, and `output/` paths; do not create a catch-all shader folder or empty future-feature folders. Preserve shader basenames and embed identities when moving files.
- Organize native scene shaders by their actual role, not merely by whether they contain a tone curve: deferred lighting composition belongs under `lighting/compose/`, visible sky/cloud ports under `sky/native/`, ocean ports under `water/native/`, and wormhole/sand effects under `effects/`. `tonemap/` contains the two named late Tonemap passes and shared curve/grading helpers. MGSV applies early tone curves in multiple scene shaders; those operations do not make every such shader a tonemap pass or move its execution later.
- Register every port under each hash its shader has. The game's shader set holds some shaders twice, with the same instructions under two hashes, and runs one of each pair; the shader catalog (`build/analysis/mgsv/mgsv-render-map/all-shader-catalog.json`) lists the hashes by source name, and `shaders.hpp` maps the twins of existing ports.
- Feature headers must not depend on being included inside `addon.cpp`'s anonymous namespace or on its hidden globals. Preserve contributor copyright and research attribution when combining files.
- Keep MGSV work inside the game folder and local development tools. Do not change shared RenoDX code, global build files, `.gitmodules`, or repository submodule registrations. Configure NRD through its public API in the MGSV adapter; keep the bundled third-party interface files unchanged.
- Plan for a D3D12 backend for ray tracing/path tracing, Ray Reconstruction, and DLSS Frame Generation. Keep scene and lighting data reusable across backends, with native API objects and submission logic contained in backend-specific code. Reuse RenoDX's `utils::gpu_fence` for cross-API GPU dependencies and existing ReShade abstractions where they cover the required operation. Follow the [D3D12 integration design](docs/ARCHITECTURE.md#d3d12-bridge).

## Settings and defaults

- Preserve established grading defaults rather than substituting personal tuning. Shadows and Global Illumination intentionally default to Enhanced, and Fog to Enhanced. New raster features default on; ray-traced and path-traced methods are opt-in.
- The two lighting mode controls use Vanilla = 0 and Enhanced = 1. Shadows uses DirectLightingShadowsMode under Direct Lighting, with additional controls under Direct Lighting (Advanced). Global Illumination uses IndirectLightingMode under Indirect Lighting and switches diffuse AO/GI and reflections together; neither half has its own mode, and the earlier IndirectLightingDiffuseMode and IndirectLightingReflectionsMode keys are no longer read. Enhanced indirect lighting runs only in the presented main view, decided by one check (`lighting/indirect_lighting_mode.hpp`) that every pass uses; other views keep native lighting. It needs the RenoDX tone mapper: under the Vanilla tone mapper it is off, its controls are disabled, and a red note above them says so (the vanilla curve runs inside deferred composition, before reflections could exchange linear light). It must not depend on any other setting without saying so in the same way. Preset Off selects Vanilla for both but leaves reconstruction selected. Enhanced reflections replace general and sortie-floor native SSR with one DX12 GGX estimator and NRD denoising. The sortie-floor path searches the camera depth; it is not a separate reflected scene. Do not add its already-shaded native image to enhanced reflections. Unresolved rays retain environment lighting; confirmed blockers occlude only the fallback, without darkening accepted screen light again. Preserve direct/diffuse light and fog in-scattering. Do not restore native SSR as a second fallback. Do not add automatic preset-conversion writes. Reconstruction selection remains independent and sticky. Reset All restores defaults; Vanilla/0 tonemapping is not full Off.
- Preserve saved keys, UI order, bindings, and reset behavior unless explicitly changing them. Key renames require deliberate handling of existing saved settings.
- Fog uses AtmosphereFogMode under Atmosphere, with Vanilla = 0 and Enhanced = 1, default Enhanced; Preset Off selects Vanilla. Its tuning controls are under Atmosphere (Advanced) and shown only with Enhanced: AtmosphereFogShadowStrength (default 100%), AtmosphereFogHeightFalloff (default 100%), AtmosphereFogUnevenness (default 100%), AtmosphereFogLocalLights (default 100%), AtmosphereFogTerrainShadows (default On) and AtmosphereFogDebugView. Local lights in the fog use the light list Enhanced shadows gather, so that control is disabled unless Shadows is Enhanced and its tooltip says so. Enhanced keeps the game's fog parameters except where the game's model is not physically accurate (the corrections and what is deliberately left are listed in the fog guide). With Fog Height Falloff, Fog Unevenness and Local Lights in Fog at 0, where the sun reaches every cell it equals the game's fog, except that it does not clamp the stored light to 1 as the game does. It runs in the presented main view only and, apart from its local lights, depends on no other setting.
- Prefix lighting keys with DirectLighting or IndirectLighting and name the contribution, such as shadows, diffuse light, or reflections; IndirectLightingMode alone names the combined indirect mode. Keep mode and strength keys independent of the raster/RT/PT backend or denoiser. Reserve Fx for controls in Effects. Add future material, atmosphere, denoising, and reconstruction controls under their own categories when implemented.
- Use the single `ShaderInjectData` layout in `shared.h` with effect-local copies for scale, history flags, and filter steps. Never temporarily overwrite shared user settings or add a second settings/control buffer. Copying is not synchronization.
- In shaders, access injected settings through the defines in `shared.h`, not direct `shader_injection` or injected cbuffer member references. Add a matching define when one is missing; do not change the shared layout just to expose a setting.
- Bind feature controls to supplied stable storage; addon composition assembles them and core preset/reset code handles cross-feature policy. Do not add another global settings registry.

## Rendering safety

- Verify each pass's actual input and output domains before changing color or lighting math. MGSV encodes scene color early in parts of its pipeline; a pre-tonemap pass or floating-point texture is not proof of linear light. Trace producer writes, sampling/view conversions, and downstream reads, and document the transfer function and any exposure or packing. Do not assume every buffer uses the same encoding.
- Before changing material interpretation or a BRDF, follow the [material contracts](materials/README.md) from CPU asset/parameter setup through G-buffer writers, palette/lookup inputs, and direct, environment, and reflection consumers. Check shader-family differences and later rain/decal writes. Do not infer a field's meaning from one channel, one shader, a debug label, or a screenshot. Record which facts are verified, which are fitted, and which data is unavailable; validate conversion and energy separately before tuning appearance.
- Verify denoiser camera conventions with captured native CPU and GPU records, including projection signs, matrix storage, world-normal rotation and positive view depth. Test actual SDK reprojection during camera translation as well as rotation; static or identity-camera fixtures can preserve the same wrong assumption as the integration. Correct mismatched guides before reducing history or tuning filters to hide movement artifacts.
- Audit depth reconstruction through the actual shader operations. A declared camera-center field does not prove it is used. Rebuild positions with the matching camera center or full inverse projection, while keeping depth loads on their original raster pixels. Distinguish the render rectangle from texture storage dimensions when decoding motion or reconstructing rays.
- For temporal motion changes, verify current and previous skin, object, and camera transforms before choosing a fix. Register meanings can differ between shaders despite generic cbuffer names. Correct the first proven precision or coordinate mismatch, and retain native deformation motion. Keep independent projection-jitter scales, alternate motion signs, and camera-only replacements in the probe rather than shipping them as settings.
- Perform light addition, radiance averaging, luminance/moment calculations, and physically based attenuation in linear light. Decode encoded color before those operations and encode back only where the next game pass requires it. Check GI gather, accumulation, denoising, and final addition separately; shadow/AO visibility factors and depth/normal/motion data are not color and must not receive blanket gamma conversions. Preserve existing alpha and packing conventions, and avoid double decoding through sRGB views.
- Treat the current AO/GI color-space behavior as requiring verification, not as proven correct or incorrect. Do not hide encoding changes inside cleanup or apply a guessed `pow(2.2)` fix; establish the actual transfer function and validate the affected lighting separately before changing it.
- Precision upgrades are mod-wide, not owned by HDR output or anti-aliasing. Make every upgrade in the engine (`engine/render_targets.hpp`); do not clone game textures or redirect bindings. Change a target's format in place only when its every use is known: list its writers, readers, and copies from probe captures first, and change both ends of an engine copy together. When other passes need the target as 8-bit, give the plugin that needs float a private image through its constructor's lookups instead. Keep shared native inputs outside reconstruction's private capture state.
- Run the diffuse AO/GI chain before the first skin scatter, preserving both scattering passes exactly once per intercepted invocation. Apply AO only to qualified native ambient diffuse, preserve direct light, and add visibility-integrated GI once. Update native diffuse and eligible copied scattering inputs while preserving their separate alpha meanings. Missing ambient inputs skip diffuse AO; missing trace inputs skip the combined effect without suppressing native work. Preserve state around the whole chain, including empty and displaced graphics bindings.
- Keep fallback inputs separate from distinct fallback outputs: unused slots still cause read/write conflicts. Preserve the depth-mip binding order and separate AO/GI output roles.
- Keep scatter inputs callback-local, not in a global pre/post frame. Retain cached native views from known-live bindings and follow selected-device/generation retirement. Retention preserves objects, not pixels; CPU recording is not GPU completion.
- Preserve original deferred command lists when canceling reconstruction. Keep new reconstruction-Off motion separate from GI's compatibility selection until producer contents, execution order, and safe history use are proven; do not substitute dummy, previous-frame, or camera-only motion.
- Keep history changes separate from ownership cleanup. Cold-history, odd-dimension, and upper-edge defects need separately approved fixes with evidence; tests that reproduce those defects do not prove correctness.
- Preserve early-registration-wins shader behavior. `on_inject = false` disables constant injection, not replacement bytecode.
- Texture resizing must not rebuild unchanged lighting pipelines. Shared FSR/DLSS preparation code must preserve their distinct resources and lifetimes.
- Keep upscaling texture-detail bias separate from explicit filter levels. Direct3D applies sampler mip bias even to `SampleLevel`; reflection roughness mips and other shader-selected levels must retain their native meaning. Verify executed samplers and the complete filter chain before treating a sharp result as a skipped pass or tuning a denoiser around it.

## Local workflow

- Builds are allowed while `mgsvtpp.exe` is running. Never deploy while it is running; keep the agreed toolchain.
- Before a probe-assisted test, deploy both the game addon and the current lighting probe, compare each installed SHA256 with its build, and check the versions loaded in the new log. After an intentional game exit, check the process as well as the window. MGSV can remain running after Alt-F4; force-close that remaining game process before deployment.
- Run builds and `clang-tidy` sequentially on Windows. File mappings from analysis can block generated-header writes. Before deployment, verify that embedded shader bytes match the current `.cso` files; successful compilation alone can leave stale embedded headers.
- Trace native producers, shader inputs, buffer ranges, blend writes, and GPU consumers before choosing an insertion point. Use existing captures and dumps first, native captures for the game's passes, and a probe for added work. Before requesting another capture, explain the missing proof and why existing captures cannot provide it. Verify inferred executable names against code and installed bytes before adding hooks.
- Prioritize robust, straightforward code when optimizing. Prefer structural improvements that remove redundant work or simplify data flow. Keep micro-optimizations only when their measured benefit justifies the complexity and the code remains clear, reliable, and easy to maintain.
- Measure at a fixed camera with On / Off / On comparisons in the same process. Report frame time as well as FPS, and separate GPU execution time from CPU recording time. A quiet recording thread can still have cached command lists running on the GPU.
- Preserve visual coverage when optimizing. If lower samples or budgets barely help, measure setup, bindings, dispatches, and empty indirect calls before changing the rendering algorithm. Removing lights or effects is a quality tradeoff, not an equivalent optimization.
- Keep probe captures, profiling, and shader reloads off until requested. Verify that the selected shader actually executed. Capture copies can remain in cached command lists; restart or verify that those lists were replaced before collecting clean performance measurements.
- Group related implementation and debug views into useful gameplay checkpoints. Check several inputs and outputs in one visit instead of requesting another run for each small edit. Keep investigation scripts and measurements under ignored analysis folders; move only lasting facts into production documentation.
- Tests are local-only: never stage or commit `test/mgsv_rendering`, temporary registration, or test artifacts. Remove task-added test wiring and verify the standalone addon build; leave unrelated local work untouched.
- For structural changes, compare compiled shaders, effective registrations, settings, and shared layouts. Report fixture results separately from actual-game evidence; use the linked verification guides rather than treating a build as visual validation.
- Follow the repository `.clang-format` and `.clang-tidy` rules when writing or editing C++; do not leave new formatting or lint violations for later cleanup.
- Before handing off changes for commit, run `clang-format` on changed C++ files and `clang-tidy` on their affected translation units using the active compilation database. Include changed headers in the lint scope, fix diagnostics introduced by the changes, and verify formatting with `clang-format --dry-run --Werror`.
- Keep formatting and lint fixes scoped to the requested changes. Do not weaken checks or add suppressions merely to silence diagnostics; report unavailable tooling, analysis failures, or unresolved diagnostics instead of claiming the checks passed.

## Reviews

A request to review a change means all of the following, without being asked for each part. Fix what the review finds; ask only when a fix would change behavior the user chose or reach outside the change.

- Check every factual statement in the changed comments, documentation, log text and commit message against its source: the code, the engine notes under `docs/`, the installed executable or its decompile, a capture, or the game log. Reword or remove what cannot be shown. A statement about the unmodified game needs evidence that does not come from a run with the mod active.
- List the assumptions the change depends on and test each one. Name the ones that stay untested.
- Walk each changed path through its event sequences: startup before a hook is selected, a settings or resolution change, a mode or quality switch, a failure and its recovery, device or swapchain teardown, and two threads arriving in either order. Compare each with the behavior before the change; a difference the change did not intend is a defect.
- Look for what the change left behind: dead state and branches, checks that can no longer fail, unused includes and engine table fields, stale comments, names that no longer fit, and documentation or local tooling that still describes the old behavior.
- Judge clarity and organization: a comment says what the code cannot, a file holds what its name says, facts about the executable are verified fields of the engine table, and nothing is more complicated than the behavior needs.
- Read the text itself: plain American English, no filler such as an emphatic "own" after a possessive, one source line per Markdown paragraph.
- For anything larger than a few lines, also get an independent review that is given the diff and its intent but not the conclusions. Check each of its findings against the code before acting on it.
- Finish with the checks in Local workflow (build, `clang-format`, `clang-tidy`, embedded shader bytes, `git diff --check`), and say what was run in the game and what was not. When the changed behavior can be reached from the title screen, run it there before reporting, including one configuration that differs from the user's.
- Report mistakes first, then what was fixed, what was left and why, and what is still untested. Say how each conclusion is known: read, measured, observed in game, or inferred.
