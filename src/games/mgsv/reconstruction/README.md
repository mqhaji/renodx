# MGSV temporal reconstruction

Temporal reconstruction combines samples from several frames to smooth edges and recover detail. Camera jitter changes which parts of each edge are sampled. Analytical TAA runs at native resolution; FSR and NVIDIA DLSS support native or reduced rendering resolution. Upscaling runs before bloom preparation and depth of field (DoF), with later scene processing and UI at output resolution.

The [addon guide](../README.md) owns build/deployment checks, the [architecture guide](../docs/ARCHITECTURE.md) covers shared ownership, the [roadmap](../ROADMAP.md) tracks future work, and [FSR installation and API details](fsr/README.md) record SDK versions and licenses.

## Usage and defaults

The Temporal Anti-Aliasing section contains the method, DLSS model, and quality selectors. Diagnostic and tuning controls are in Temporal Anti-Aliasing (Advanced), collapsed by default. Reconstruction stays independent of RenoDX presets; Off restores the original projection and FXAA. Settings load without automatic conversions.

| Control | Behavior and default |
|---|---|
| Temporal Reconstruction | Off (Vanilla FXAA), Analytical TAA, FSR, or NVIDIA DLSS; new profiles use FSR |
| DLSS Model | Presets A-F and J-M when supported by the DLL; F is default/reset, saved as 6; unavailable hints fall back to the DLL default |
| Upscaling Quality | Auto, Native, Quality, Balance, Performance, or Ultra Performance; default Auto; available for FSR/DLSS on the supported executable |
| TAA Clip Tightness | Blends broad history bounds toward a tighter cross-shaped neighborhood; default `0.50` |
| TAA History Clip Strength | Restricts history to current color bounds; default `1.00` |
| TAA Current Frame Blend | Maximum filtered current-frame contribution; default `0.15` |
| TAA Diagnostic View / Velocity View Range | Read-only motion and color views; default Temporal Resolve and `8 px` |

Auto follows NVIDIA's [UI guidelines](https://github.com/NVIDIA/DLSS/blob/main/doc/RTX%20UI%20Developer%20Guidelines.pdf) by total output pixels: Native below 1920x1080, Quality through 2560x1440, Performance through 3840x2160, and Ultra Performance above that. This includes ultrawide displays. Auto does not measure frame rate or run dynamic resolution; manual choices override it, and DLSS queries its SDK for the selected mode's supported input size.

FSR uses approximately 2/3, 1/1.7, 1/2, or 1/3 of each output axis for Quality through Ultra Performance, rounded to even dimensions. At 3840x2160 output these are 2560x1440, 2258x1270, 1920x1080, and 1280x720. Both SDK methods use `ceil(8 * (output width / actual render width)^2)` jitter phases, with a minimum of eight. Native uses eight phases; Analytical and Off retain native sizing.

FSR/DLSS add `log2(actual render width / output width) - 1` to pixel samplers used for automatic texture-detail selection. Native adds -1; Off and Analytical retain the game's bias. Explicit mip choices keep their native bias because they can encode roughness, blur width or another filter quantity. Direct3D applies sampler bias even to `SampleLevel`, so applying the detail bias globally changes reflection blur. Shader bytecode is inspected once at creation; a sampler shared by automatic and explicit sampling keeps its native bias. Unknown shaders and unsupported operand indexing also remain unbiased. No shader-name list or compensating mip offset is used. The cache keeps one bias value, while bound contexts and recorded command lists retain their own sampler references. Size/quality changes rebuild size-dependent resources and restart history; changing visualization range alone does not reset it.

Failed output allocation, an unsupported native path, or repeated failures with otherwise valid inputs request native-size recovery. The quality choice stays saved. Select Native, then another quality mode to retry. Missing startup camera/motion data can recover normally. Only the native scatter DoF path is supported; other DoF paths request recovery instead of resizing unknown work.

## Code ownership and output routing

Where to look:

- [post_filter.hpp](../engine/post_filter.hpp) hooks the point where the engine starts a view's post-processing. Every scene's reconstruction is scheduled there.
- [input_capture.hpp](input_capture.hpp) builds the scene's inputs at that point and holds every check they must pass, in one list. The images come from the engine's targets ([render_targets.hpp](../engine/render_targets.hpp)); the camera is the one recorded for the same view.
- [motion_vectors.hpp](../engine/motion_vectors.hpp) keeps the engine drawing motion vectors while reconstruction or enhanced indirect lighting is on, so reconstruction does not depend on the game's motion blur setting. The engine creates both velocity targets as RGBA16F.
- [dispatch.hpp](dispatch.hpp) schedules the scene's job, which [submission.hpp](../rendering/submission.hpp) cuts into the command list and runs when the game plays the list back.
- [runtime.hpp](runtime.hpp) manages the requested and effective methods; [settings.hpp](settings.hpp) binds the controls to addon-owned storage. The shared [input owner](../rendering/inputs.hpp) selects one device and swapchain.

Reconstruction does not look at individual draws. The lighting history records the motion and camera it uses from the engine's camera-velocity hook (`OnCameraVelocityRecorded` in `runtime.hpp`), once per recorded pass, while enhanced indirect lighting needs motion.

[Native view ownership](../engine/views.hpp) follows each scene build into its worker jobs. Camera and motion records are selected by that scene and presentation generation. The submission bridge carries the copied scope into immediate-context evaluation. Post-processing checks the same owner before choosing a recording route, a continuation on another command list, or the active output. Full-clear records carry the owner too. This prevents fixed-size rain work from selecting a main-scene route through a pooled texture or a reused worker thread.

The first Present selects the game's main swapchain and connects native ownership to it. Swapchain creation can happen before that selection. When the main view ends, its enclosing renderer retains the scene ID for final display conversion, which runs outside the view scope. Display completion releases that scene's recording sequence while other scenes keep their routes.

[frame_inputs.hpp](frame_inputs.hpp) separates render and output dimensions. The output size is the render size the game requests, which follows its resolution setting, not the window size. In the game's borderless mode the window and back buffer stay at desktop size; everything from the upscale to the UI runs at the output size, and the game's last pass scales the result to fit the back buffer, centered and with its aspect ratio kept. The engine sizes that rectangle from its render size, so [output_size/runtime.hpp](output_size/runtime.hpp) makes the same fit for the output size. [resolution.hpp](resolution.hpp) requests native renderer size changes through its normal update, not around individual draws, and adapts DoF rectangle/sprite-grid arguments. [mip_bias.hpp](mip_bias.hpp) owns replacement samplers. Native hooks check the executable and expected code before installation.

[output_size/resources.hpp](output_size/resources.hpp) owns enlarged scene/intermediate textures, typed views, and depth/stencil copies. [output_size/runtime.hpp](output_size/runtime.hpp) routes native draws/copies/clears and restores their bindings. Its helper shaders share [32-byte copy constants](output_size/copy_constants.hlsli). The engine is not switched to output size for post-processing instead, because its sizes are shared state that scene jobs still read. Every post pass sizes itself from the backend's render size: through the size getters, through the view rectangle and the G-buffer size copied from it, and through the primary render buffer on top of the backend's stack. In every probe capture (title, hillside, Mother Base), 3 to 17 scene worker jobs (geometry, decals, sun shadows, local lights, spherical harmonics) are still recording when the build thread enters post-processing, and model and terrain level-of-detail in those jobs reads the view rectangle. Switching those values would race with the jobs; the redirection changes only bindings on the command list that records each post draw. Native source names and reflected texture/constant reads identify supported 2D shaders; no external dump is needed at runtime.

Geometry, lighting, and native SSR use render dimensions. DoF, motion-blur color work, grading, and UI use output dimensions; search reaches are converted from output to render pixels. Fixed-size UI, utility, and scene-thumbnail targets retain their own sizes. Generic CopyRenderBuffer must actually read a routed image at t0 before a destination can be resized; stale unused slots and matching dimensions are insufficient.

Source geometry depth is resampled separately from UI depth/stencil, including current jitter. Native depth and all eight stencil bits are retained. UI depth uses one fullscreen draw and stencil uses eight fixed masked draws. Native copies/clears, rectangles, viewports, scissors, and the size fields actually read by each shader follow output dimensions. Disabled hardware depth/stencil tests allow a DSV to be detached temporarily; active tests require a matching output-sized target. Sampled scene-depth reads remain separate.

Bloom keeps a 246x138 working region inside output-sized reduced buffers. Size constants adjust reduction offsets, flare center/fade, and the final crop independently of Bloom Type. At 4K, quarter-axis buffers remain 960x540 across quality modes. The [bloom guide](../postprocess/bloom/README.md) owns filtering/color behavior. One bloom image is reused for DoF controls, which keep their data range rather than receiving color conversions.

DoF sprites sample their enlarged bake inputs in both vertex and pixel stages. Radius limits and first-bake cutoffs follow output width. The native DoF plugin supplies its viewport, camera, and effect instance. Those identities must match the selected scene and its applied size plan before the addon copies and scales the blur parameters. Each invocation has its own token, and nested calls restore their caller's state. Within that invocation, `DgResources::SetRenderArea` receives the shared DoF resource object and establishes the output-sized rectangles. `DepthOfFieldDx11::DrawSpriteSub` receives the effect instance and uses the matching output-sized sprite grid. Auxiliary views keep native parameters even when their dimensions match the main scene. Post-processing also checks the scene, presentation generation, invocation, and first bake's scene-color input before enlarging DoF targets.

Backend sizing waits for a main view associated with the selected swapchain. Startup can render at native size while that association is established; the next native backend update applies the requested scale automatically. A missing association restores the game's size request on a previously selected backend. Unrelated backends remain unchanged. Destroying the selected view or renderer, changing its membership, or replacing the presentation retires the association.

Shaders reading view-to-buffer ratios receive copied size fields, with a small compute adjustment where needed. Multiple adjustments share one state save; native DoF viewports already at output size are not scaled twice.

The depth-tested flare-sprite pass `0x93A0C8D8` writes a separate half-size layer. Its depth is matched to current scene geometry while typed views, blend equations, native shader, clear color, and alpha are retained. That layer keeps its producer/consumer mapping across frames because another worker can record its scene copy before the flare draws. Frames without flares keep a neutral layer through native clears. Native quality retains the original route.

Each scene reserves its own output and intermediate roles. Workers recording the same scene share that allocation. Deferred contexts retain each output until successful `FinishCommandList` transfers those references to the native command list. This includes earlier draws whose display conversion has finished. Immediate-context calls rely on submission order and release their temporary references after issuing commands. Display recording releases the open sequence, while the pool keeps its scene identity and producer roles for UI recorded later on another worker. Those lookups share the existing image. The pool can assign a new owner after recording contexts, open sequences, and retained command lists release the allocation. Compatible spare allocations remain available for overlapping recordings. Free allocations with a different input layout are retired. D3D11 submission order keeps new GPU writes behind earlier submitted users. Resets retire the pool while outstanding lists retain their resources.

Full clears are recorded by native resource and scene identity. Known output targets receive clears at their original command position. The first qualified cropped or blended write can also recover a clear recorded before allocation. Output acquisition transfers earlier clears to the scene's producer, which retains them across display recording for parallel workers such as lens flares. Output reuse releases those records with the old producer. Startup scenes that never acquire output release their pending clears at display completion, preventing an ever-growing lookup table. Matching scene dimensions alone cannot allocate an enlarged intermediate. Loading UI can reserve scene storage through its qualified clear while ordinary post-processing waits for reconstruction admission.

Creating an enlarged target does not make its pixels valid. Draw routing checks targets, active depth/stencil, rectangles, and required constant buffers before clearing targets or recording intermediate roles. A rejected draw leaves earlier output pixels, producer roles, and native bindings unchanged.

When shader reads are known, the supported native constant layout must fit both the allocation and the bound D3D11.1 range. Missing buffers or insufficient ranges reject the enlarged route, including DoF sprite vertex constants. Constant preparation follows GPU command order. Replacement buffers are bound only after the whole draw is accepted. Allocation or range failure must not mix native dimensions with enlarged targets.

Each output allocation shares immutable size constants between intermediates at the same reduction level. The system and Kawase adjustment shaders copy their complete native prefixes into scratch storage while replacing the required fields. A single buffer copy installs each result. Larger allocations first preserve bytes outside that prefix. Every recorded adjustment still reads its source during GPU execution, including repeated command-list execution after the game changes the source buffer. Reusing a buffer address alone cannot establish that its contents are unchanged.

Target preparation resolves each native intermediate once per draw and carries its resource, replacement view, and previous write status through clear handling and final validation. The allocation stores immutable native/output dimensions for rectangle and constant preparation. A cached target view can be read under a shared lock. Creating a view requires an exclusive lock and a second lookup to handle concurrent workers. Producer membership and roles are checked for each draw and published only after all required bindings pass validation.

Input preparation returns each sampled view and its producer-qualified role together. Repeated bindings of the same view share that result within the draw, including DoF vertex inputs. Different views of one texture keep their own format and subresource settings. The next draw resolves its inputs again so reused native storage cannot carry a previous producer's role forward.

Only texture slots read by the pixel shader are remapped. Native order remains late tonemap, FXAA, then UI even when UI records first on another worker. Draw2D normal-blending, normal-encoding, and roughness-blending shaders produce packed data, not UI color. Treating all Draw2D shaders as UI previously redirected rain/material work incorrectly.

Generic Draw2D routing also requires one origin-aligned viewport covering the full render or output extent before any bindings change. The game uses the same shaders and pooled scene/depth textures to initialize fixed-size captures, including rain occlusion; those smaller views must keep their native color and stencil writes together. Scissor-clipped main-view UI still routes normally. Explicitly identified post-processing passes retain their own cropped-view rules.

Loading/save reload may draw UI without a new scene. UI and display conversion share the matching output allocation, and native color/depth/stencil clears reach it even when no reconstruction dispatch runs. The original clears still execute. Cancellation or replay fills output from current native scene data before the remaining game work continues.

## Frame and resource contracts

1. The main SetViewMatrixState hook reserves one jitter sample for the native scene, saves its unjittered matrices, and offsets gameplay projection at `ShaderManager+0x680`. Repeated setup and supported worker paths reuse the scene's saved sample. Recording the next scene reserves its next sample independently of reconstruction completion.
2. The engine's targets supply scene color (`PRIMARY_COLOR_BUFFER` `0x90EBFD910903`), G-buffer depth (`DEPTH_BUFFER` `0x5DD84A404FCB`), composed motion (`0x803A4617E25D`) and object motion (`0xFE772C3902FD`) to every method through `ValidatedFrameInputs`, with the shader views the engine itself binds. While temporal reconstruction is on, the mod's velocity shaders write both motion images in precise form (see Motion and reconstruction). The camera is the one recorded for the same view build, and the motion vectors count only if that build ran its camera-velocity pass.
3. Reconstruction has one insertion point and no fallback: `DgDx11::StartPostFilter`. The engine calls it once per view, on the build thread, after the last scene writer (transparent effects) and before the first post pass. No command list is open at that moment, because the engine opens the next one at its first post draw. So the hook marks the scene, and the mod cuts that list as soon as it begins (or at once, if a list is already open). Bloom, depth of field, motion blur, grading and UI all read the reconstructed image, and none of them has to be enabled for reconstruction to run.
4. At the cut, each scene gets one of three outcomes. It is reconstructed when its inputs are complete. It is filled when the mod is upscaling but the motion vectors or the camera are missing, as on startup screens: the job scales the native image into the output, and the next reconstruction starts fresh history. Otherwise nothing is scheduled, because no scene image is usable or the list cannot be cut. The log names the cause once each time it changes. If eight upscaled frames in a row have complete inputs but are not reconstructed, upscaling ends; frames with incomplete inputs never count toward that.
5. Immediately before evaluation, the dispatcher derives reprojection from the last successfully installed scene. A consecutive reservation with matching camera, viewport, dimensions, and generations can use history. A gap starts fresh history. Only successful evaluation and output installation advance the saved endpoint. Cached replay preserves native commands and refreshes scaled output through the spatial fallback without evaluating the same temporal observation twice.
6. Enabled reconstruction bypasses FXAA filtering but preserves the draw's other scene processing. Scene alpha remains current-frame data for downstream DoF/highlights.

Inputs must match native scene, presentation generation, device, dimensions, layout, and reset generation. Their saved jitter remains valid across Present and newer scene recording. A view build starts post-processing once, so each scene is scheduled once; a second start in one build is ignored and counted. An SDK evaluation that fails output installation invalidates backend history. Size, method, and relevant setting changes also restart accumulation. While the mod is upscaling, the engine's render-size path does not present a correct image (its depth of field and motion blur then combine images of different sizes), so a scene that can be filled always is.

[dispatch.hpp](dispatch.hpp) runs reconstruction between preserved native D3D11 command-list prefixes and remainders. Shared input preparation runs on D3D11; all three methods evaluate on the private D3D12 queue and return encoded output before native post-processing. The exposure meter keeps measuring the native render-size image: its first image (`0x80726D23BE27`) is tagged when the engine creates it, and the copy that feeds it never enters the output-size route. Usually the meter reads the diffuse light buffer, but on startup screens it reads scene color. See the [backend ownership and submission guide](../docs/ARCHITECTURE.md#d3d12-bridge). Changing methods cancels obsolete reconstruction, not game commands. [GT-VBGI](../lighting/indirect/README.md) uses the same native scene ownership metadata but retains its D3D11 passes and its own submitted camera/motion and history ledger, including with reconstruction Off. Retained objects and CPU recording order do not prove matching pixels or GPU completion.

| Signal | Required form |
|---|---|
| Scene color | Render-sized RGBA16F containing MGSV's encoded scene RGB; decode before light calculations |
| Alpha | Current-frame native alpha, preserved at equal size and clamped-bilinear resampled when output is larger |
| Depth | Render-sized reverse-Z from velocity composition; larger raw values are nearer |
| Object/composed velocity | Separate RGBA16F images; native motion is packed in `.ba`, with object mask in `.r` |
| SDK inputs | Linear RGBA16F color and signed RG16F motion; DLSS also uses an R32F reverse-Z depth copy |
| Output | Native reuses the existing scene target; reduced-resolution FSR/DLSS use a separate output-sized target; Analytical requires equal sizes |
| Camera history | Double-precision unjittered matrices, saved only after successful matching output |

Shared SDK preparation constants are 96 bytes: current jitter, camera validity, render size, camera reprojection, and the Analytical debug-output flag. State restoration covers compute/graphics shaders, class instances, texture views, render targets, blending, depth/stencil, descriptors, and native constant-buffer ranges. FSR must preserve the same full state as the other methods.

The shared [D3D11 compute-state helper](../rendering/d3d11_state.hpp) retains the native bindings affected by added compute work. D3D11 getters capture every relevant slot, including empty slots and graphics texture views that a compute output can displace. Added work uses the native context or ReShade commands, which leave game-state tracking untouched. Restoration removes temporary compute bindings before restoring the saved resources, compute shader and class instances, and output-merger state.

## Native jitter ownership and lifetime

[projection_jitter.hpp](projection_jitter.hpp) accepts an enabled, full-resolution perspective viewport whose original projection matches the shader manager's copy. Setters change only `P[8] += 2*jitter_uv.x`, `P[9] -= 2*jitter_uv.y`, and required dirty flags. Path scales multiply these offsets; unrelated elements stay intact.

Depth-based position reconstruction needs the same projection center as geometry. The native scene-bank flush adds `+2*jitter_uv.x, -2*jitter_uv.y` to camera-center register 28 in a private upload copy, and the skin-scattering upload applies the same correction to its separate 64-byte geometry block. Both hooks validate the saved scene, viewport, camera, original matrices, dimensions, and reset generation. They copy only qualified native values and preserve any original lens shift. The flush retains native dirty and binding updates, restores its original CPU source pointer, and never forces an extra upload. Already-corrected or unrelated inputs pass through unchanged. The shared camera object and SDK matrices remain unmodified.

Native lighting, scattering, AO/GI, and reflection rays subtract that corrected center once when reconstructing positions from depth. Projected lookups restore it once. They must not also subtract or add temporal jitter explicitly. Motion preparation still removes current projection jitter from native object velocity because the SDK expects motion between unjittered image positions; that is a separate conversion.

- Original paths are Velocity, Forward, Model, Alpha Model, Overlay Model, and Local Light. Local Light applies the scene's jitter to its completed draw packet before the game copies or queues it for workers. The publication lock covers camera validation and that write, then releases before the native call. Workers inherit the corrected projection through the game's packet ownership.
- Velocity, Thermography, Forward, Model, Alpha Model, Overlay Model, and Local Light validate the scene's saved camera, viewport, original projection/view matrices, dimensions, and reset generation. Later scene recording and Present leave that saved sample intact. One publication lock covers validation and the native write. Secondary cameras require their own qualified scene, and an already-offset projection receives no second offset.
- Experimental paths retain the same scene and reset identity through their temporary matrix edits. Lock order is transition, execution, then camera data. Release guards before native calls, allocation, or logging. A rejected nested call must not inherit another call's valid correction.
- Reject unrelated, stale, orthographic, nonfinite, already-offset, or ambiguous data. Deferred camera packets need their actual producer sample/reset association, not the latest matrix or a matching pointer.

Every corrected native pass uses the same saved scene sample. Independent jitter multipliers, alternate motion formulas, and jitter-Off sampling are not production settings. Analytical motion debug views visualize the inputs without changing their calculation. Draw2D billboard, glyph, and alternate-camera staging stays native; no inactive hooks are installed for those paths.

### Native projection paths

Addresses below are hexadecimal offsets in the supported executable; verify them before using another build. `P` is projection and `VP` is combined view/projection.

| Native pass | Route and restriction |
|---|---|
| Sun volume | `30AC50 -> 30B680`, return `30B07D`: private aligned VP copy for synchronous upload/draw |
| SH lighting | Deferred producer `281EF0` attaches its owned packet at `283B90`, return `282A8B`. Render P at `+160` supplies both volume coverage and inverse-position evaluation. Immediate helper `27EF80`, return `1F2529`, offsets successful clip XY. |
| Terrain decal | `275280 -> 2D18D0`, return `2755CA`: owned packet P at `+160`; affects inverse-plane reconstruction, not separate raster projection |
| Sky / follows scene sample | `1F50D0`, return `1F5990`, finishes inverse projection rows at parameter offset `+40`. Correct those rows before `306D10` uploads the sky constants. |

Clip translation adds jitter times W to XY, preserving Z/W. The immediate SH helper validates every output before writing, with 8, 6, 18, or 8 vertices for kinds 0 through 3. Native packets retain their reference-count headers and owned storage. Constant `0x47` selects bank 7, vectors 4 through 7. The verified graphics flush at `2C5A10` binds that bank to D3D11 constant-buffer slot 7. Null-camera updates can leave old context matrices, so those matrices must not be changed permanently.

Deferred SH follows the scene through its producer scope. The attachment hook checks the packet's copied view and original projection, then corrects render P before either worker retains it. The sphere-map worker fills the light list. The draw worker at `280060` derives both its projected vertices through `27F450` and its inverse light-volume coordinates from that corrected P/V pair. Worker execution therefore carries the producer's sample even when another scene starts recording. The publication lock ends before the native attachment call.

Sky uses a separate inverse projection to turn fullscreen clip coordinates into world-space rays. The native builder stores inverse rows, and the constant upload copies them directly. The hook verifies that this inverse reverses the scene's original projection, then composes the inverse clip translation into its fourth column. The sky vertex shader receives rays that match the jittered raster projection. The correction validates the scene and reset generation again after the native builder returns.

Terrain decal evaluation reads render P/V from its retained packet, while `SetWorldMatrix` uses the worker command's P/V for rasterization. The local probe records both pairs to check their agreement in actual draws. A later scene executed the terrain-decal worker at 1920x1080 input. Its packet and raster P/V matched exactly, and its scene and command node joined to executed NewTerrain_Decal draws on the same grid.

Draw2D can switch cameras while handling billboards, world coordinates, and glyphs. Its staging requires separate camera ownership before any selective correction. Terrain alignment, sunlight coverage, and SH coverage still need broader gameplay checks.

The Local Light hook intercepts `RequestDrawAllLocalLightOnJob` at `2A43E0`, called from `PluginLocalLight::MainExec` with return address `20B8A3`. It verifies the packet's render P/V and viewport rectangle against the qualified scene, then offsets render P at full packet offset `+1A0`. The game's unshadowed-light jobs copy this context immediately. Its shadowed-light job retains the packet and copies the same context into per-light jobs later. Culling P/V and frustum planes keep their original values. The shared viewport stays read-only, and an already-offset packet fails the original-matrix check. MainExec's alternate early path only prepares and combines light buffers. The separate local-light selection worker at `2CB160` never reads its packet's VP, so it needs no correction.

Camera hooks remain installed for the process lifetime. Device destruction stops work but does not unpatch hooks or free trampolines; recreation reuses them. Install at device initialization, never from a slider callback. Restart MGSV before replacing/removing the addon. Do not wait for callbacks under a lock they need, and do not assume Off/reset can cancel already submitted work.

## Motion and reconstruction

Native `.ba` decodes to `(ba*2-1)*64/render_size`, a current-minus-previous UV delta. Analytical reads history at `output_uv - velocity`; FSR/DLSS preparation converts to their current-to-previous convention. When a neighboring pixel supplies motion, apply its motion to the output pixel's UV. Camera motion comes from depth and unjittered matrices; object motion retains bone movement with current projection jitter removed.

Analytical selects the nearest depth from the center and four diagonals, carrying velocity, mask, depth, and UV together; the last equal-depth tap wins. FSR/DLSS use the center. Analytical stores linear RGBA16F history on D3D12. Each 8×8 group shares a 10×10 current-color tile, and sixteen point reads reconstruct the signed Catmull-Rom history filter without repeated gamma decoding. The resolve writes encoded game output alongside linear history. It uses one Shader Model 6.0 target compiled with DXC; the algorithm needs no later shader-model features or compatibility variants. It has no previous-depth rejection or history locks.

The game encodes motion for an 8-bit image: B and A map -64..64 render pixels to 0..1, and in the object motion image R is the moving-object mask. In the 16-bit float targets this rounded small motion to 1/32 or 1/16 of a render pixel, which showed as a slight wobble on slow-moving characters, clearest on the ACC title's idle character. While Analytical TAA, FSR or DLSS is selected, ports of the velocity shaders write both motion images in precise form instead: signed render pixels (y down) in B and A, unrounded and without the 64-pixel limit, marked with 1 in G (`rendering/motion.hlsli`). The G-buffer pair writes object motion; the camera-velocity port writes the combined image, camera motion from depth replaced by object motion under the mask, and reads object motion in either form. The game's shaders, its clears and its 8-bit motion blur tile images leave G at 0, so each pixel says which form it holds; `GBuffersBase_ps` and `GBuffersBase2_ps` also encode velocity and are not ported, so their pixels stay in the game's form. Every reader decodes by that mark. Input preparation and reflection preparation read object pixels from the object image and use the combined image only where camera motion cannot be computed from depth. While the sprint blur effect is active, the engine draws its material (`Draw2D_TPPSprintCameraBlur_ps`) into the combined image in place of the camera-velocity shader; that shader reads only depth and writes the game's form. The game reads the combined image in two motion blur passes, ported for this: the tile pass, whose first draw reads it, and the velocity and depth bake. Both apply the game's 64-pixel limit when they read precise motion, so motion blur behaves as before; their tile and baked images stay 8-bit in the game's form, so motion blur itself gains no precision. `MotionBlurLengthVelocity_ps` would also read it, but the engine never draws it: its handle is used only where motion blur is created and released. In the executable, only the three screen-space velocity functions bind the combined image as a target and only the motion blur functions read it as a texture; the engine also binds the object image for deferred shading and local lights, at texture slots that no game shader reads it from. Non-finite motion (a previous position at or behind the camera plane) is written as no motion, and motion longer than twice the larger render dimension is shortened to that length, which still points off screen and stays inside the 16-bit float range. With reconstruction off, the game's shaders run unchanged. With precise motion in both images, the wobble is gone at the ACC title and motion blur works as before.

The two verified character-motion vertex programs use b2 c12-c15 for previous model-to-world and c16-c19 for previous world-to-clip, despite their generic shadow-matrix names. Large world coordinates can lose subpixel precision during those float operations. At the verified model-worker upload, the native constant hook combines these matrices in double precision on the CPU and uploads the float result followed by identity. This preserves the native shader's two-matrix interface. The original vertex shader, current position, bone motion, alpha tests, and packed output remain unchanged. Shader creation identifies the exact native vertex/pixel programs; the upload requires a matching pair bound to that worker's D3D11 context, at the verified call site after shader bindings are flushed. These fields have other meanings in lighting shaders, so unrelated programs retain their original values. The precision correction uses the native matrices from that upload and stays active with reconstruction Off. Only jitter corrections require the published reconstruction camera. No GPU pass, buffer allocation, or per-vertex double arithmetic is added.

## SDK lifecycle

FSR loads AMD's signed loader and upscaler DLLs beside `mgsvtpp.exe`. AMD selects the newest compatible provider, which is logged when the context is created. FSR uses the same D3D12 device, queue, shared inputs, and output encoder as the other methods. The DLL owns its shaders, scratch resources, and history. Accumulation and shading-change tuning use AMD's defaults; automatic exposure is enabled, `preExposure = 1`, and optional sharpening and external masks are unused. See [installation and API details](fsr/README.md).

DLSS needs a compatible `nvngx_dlss.dll` beside the game executable and NVIDIA's installed NGX core. The addon does not bundle it. Unidentified/non-NVIDIA adapters show an explanation; NVIDIA hardware alone does not establish support.

- Inspect/load DLSS only after explicit or saved selection. Initialize at Present, outside draws. Keep the current method, shader binding, history, and render size while initialization is pending. At startup, Off remains active until DLSS is ready. Re-read the user's choice after initialization so cancellation cannot reactivate DLSS. Support failure stays explained until restart rather than retrying every Present.
- Shared submission/query tracking starts at Present when a temporal method is selected and remains through method switches. Analytical/FSR do not load NGX. A preexisting deferred recording requires a known successful FinishCommandList, or a context created after tracking began; reset/Present/failed Finish is insufficient.
- NGX records creation and evaluation into the shared D3D12 command list. The bridge submits that list after evaluation and output encoding have both been recorded. Submission/state/query/NGX failures request Off; model rejection is tracked separately per quality mode. DLSS uses automatic exposure and no sharpening.
- Switching away releases the inactive method's private GPU resources before evaluating its replacement. DLSS releases its feature, parameters, and output with `FreeMemOnReleaseFeature` enabled so NGX frees cached feature allocations. FSR destroys its context and output. TAA releases its pipeline and history. Keep SDK libraries and NGX initialization until device teardown; returning to a method creates a new feature/context with fresh history without a second capability probe or a temporary Off transition. Shared D3D12 transport stays available to the active method.
- Method changes wait for submitted GPU work before releasing feature resources; ordinary frames never wait on the CPU. An idle SDK is not evaluated and submits no reconstruction work. If completion or feature release fails, report the failure and retain resources still in use. Device teardown shuts down our NGX instance and releases our AMD DLL references without removing references owned by another consumer.

Method switches must not pass through Off while initializing a replacement: the native backend treats Off as a request to restore display-sized rendering. Standalone checks cover first-time DLSS selection from active FSR, cancellation, repeated switches, fresh features, HDR output and alpha, rejected-input recovery, and native/scaled input admission. The November 14 ACC test started with FSR saved and passed FSR → DLSS → FSR → DLSS with a normal image. The log confirms 1920×1080 input to 3840×2160 output throughout those switches, without an intermediate Off transition or an upscaling failure. The same run also returned to DLSS after selecting TAA and Off. Broader gameplay and device teardown still need coverage; FSR 4 needs compatible AMD hardware.

## Manual validation

Follow the [addon deployment instructions](../README.md#build-and-deploy), restart with one matching addon, and disable live shader overrides. These checks cover scene reconstruction; the [lighting guide](../lighting/indirect/README.md#build-and-gameplay-checks) covers its separate history/filtering.

1. Check fresh defaults with FSR, Auto, DLSS F, nine Analytical scales at `1x`, and diagnostic UI. Presets must not change reconstruction, and Off must restore FXAA/projection without a lasting shift.
2. Start Analytical/FSR without selecting DLSS. Check no NGX load, successful accumulation, and no repeated resets in static menus or smaller DoF draws.
3. Compare static detail, characters, hair, foliage, wires, camera motion, binoculars, cuts, menus, pause/resume, fog/rain, bright moving lights, SSR, skin, DoF, motion blur, and night vision. Separate wobble from ghost trails; keep Unclamp Off for baseline tests.
4. Exercise every method/quality and DLSS model switch. Launch with DLSS Auto saved and check performance before changing quality. Test cancellation, missing-DLL/unsupported-device explanations, feature release/recreation, resizing, window/fullscreen changes, device lifecycle, loading/save reload, and Off/Analytical restoration. Check UI clipping, subtitles, and scene alpha.
5. Compare FSR Performance and Native, then DLSS qualities. Check render/output dimensions, depth edges, near/far DoF, flare-layer clearing, bloom crop, motion blur, contact-shadow/GI reach, and the reported ACC/Mother Base/sortie problems.
6. Test experimental path scales and rejected/nested/foreign-camera cases separately. Verify a stable settled waveform with Analytical/FSR/DLSS; keep Preset M rail flicker separate from Alternate Stream behavior. Do not repeat inconclusive Auto/Direct sweeps as evidence of a fix.
7. Read the fresh log for allocation/input/query/state/NGX failures and repeated history resets. One `first cut at the engine's post-processing start` line and `reconstruction inputs are complete` identify normal operation; `reconstruction inputs are incomplete: <cause>` says why scenes are being filled or skipped, once per change of cause. Render/output sizes match at Native and differ under upscaling. A recorded dispatch does not prove GPU completion or visual correctness.
8. For backend changes, run the local D3D11/D3D12 checks for color, alpha, resource states, resizing, and queued submissions, then check the affected methods in game. Compare performance at the same camera and quality with identical probe settings, the overlay closed, and no alt-tabbing between readings. The [bridge guide](../docs/ARCHITECTURE.md#d3d12-bridge) explains ownership and synchronization; the former Copy/Verify test modes are no longer part of the addon.
