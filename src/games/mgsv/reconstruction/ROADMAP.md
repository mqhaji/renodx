# MGSV reconstruction roadmap

This page tracks outstanding work. The [reconstruction guide](README.md) owns current behavior, defaults, [known limitations](README.md#known-limitations-and-validation-status), and the [manual test matrix](README.md#manual-validation). Resolution scaling and basic quality switching have gameplay coverage, but cold startup, loading, resizing, special views, DoF focus edges, and missing-input recovery still need broader checks. No new performance gain is established by the file cleanup.

## Character motion and pose correspondence

- Establish same-character color/velocity correspondence through semantic vertex elements, referenced vertex/index/skin data, object/instance identity, and the history actually accumulated. Shader input registers are not vertex-buffer slots, and matching all bindings or POSITION alone is insufficient.
- Match the current color pose to current velocity and the previous velocity pose to the last accumulated color. Account for deferred execution, cached-list replay, skipped updates, and writes between motion composition and SDK preparation. Matching SRVs, first-bone values, CPU ordering, and successful readback do not establish matching pixels.
- Native previous viewport matrices advance independently of addon history. The external velocity dispatcher at plugin `+0x68` / virtual `+0x30` and per-object inclusion remain unresolved. The descriptor pool is not a bone uploader. Prove a usable same-character pair before requesting another generic diagnostic run.
- Analytical Jitter Off and Auto/Direct motion comparisons did not resolve wobble; Matrix Camera Everywhere caused too much ghosting to judge it. DLSS has also shown wobble. Keep Direct Object (6) and Auto Center Pixel (7) as diagnostics, and do not change motion sign/scale or relax frame/reset guards without evidence.

## D3D12 rendering and frame generation

The planned ray tracing/path tracing backend, DLSS Ray Reconstruction, and DLSS Frame Generation target D3D12. Current raster and reconstruction work should preserve the information those features will need.

The backend must support custom compute and raster passes, FSR through its SDK DLL, DLSS Frame Generation, ReSTIR sampling, SHARC radiance caching, NRD denoising, and DLSS Ray Reconstruction. Share scene identity, camera and jitter conventions, material and light descriptions, encodings, and history validity across backends. Keep native bindings and SDK lifetimes inside their owning backend. Add interfaces when a concrete consumer needs them.

The [bridge guide](../docs/ARCHITECTURE.md#d3d12-bridge) owns the current resource, synchronization, and diagnostic rules. Its tested color round trip is the starting point; depth, motion, persistent histories, and reconstruction evaluation are next. Ray/path tracing will also need geometry and pose capture, acceleration structures, and material evaluation. Preserve the distinction between radiance, material response, and visibility.

### Next D3D12 reconstruction checkpoint

Move DLSS, FSR3, and Analytical TAA evaluation onto one D3D12 backend after committing the bridge. Keep the current BeforeBloom insertion, scene-owned jitter, history advancement, and post-processing route. The current bridge test runs an identity compute shader after D3D11 reconstruction; ordinary rendering with the test Off still uses D3D11 throughout.

1. Extend shared allocation and submission to accept distinct input and output sizes and multiple signals. Carry the accepted scene, presentation generation, camera reservation, jitter, reset state, and render/output dimensions together. Add typed depth and motion formats with hardware checks. Retire descriptors, constants, shared images, SDK contexts, and history resources according to their last GPU use. Persistent histories belong to the reconstruction method, separately from reusable per-submission storage.
2. Reuse input preparation as the transfer into shared storage. DLSS and FSR already decode MGSV's sRGB scene color and construct motion in a compute pass. Write those results directly into shared linear color, reverse-Z depth, and motion textures, then signal D3D12 once for the complete input set. Preserve current alpha for DoF. This initially leaves the native-input conversion on D3D11 and removes the need for separate raw-image copies and an identity pass.
3. Evaluate DLSS through NGX's D3D12 entry points and FSR3 through the signed FSR API DLL. Query and record the selected FSR provider and version. Preserve the current method, model, quality, motion scale, jitter sign, exposure, and reset behavior. Keep SDK-specific descriptors and context lifetimes in their existing method folders. Use the bridge's direct queue for the first implementation and measure before adding queues.
4. Port Analytical TAA's resolve and history to D3D12 in the same checkpoint. Its current shader already decodes individual color/history taps and encodes its output. Preserve that sampling behavior and its raw motion diagnostics during the initial port. If preparing linear TAA inputs can remove repeated conversions, compare the result explicitly because FP16 rounding and history representation can change it. TAA remains native-resolution unless separately extended.
5. Record the output conversion immediately after reconstruction on the same D3D12 queue. Reuse `encode_output.hlsli`'s sRGB encoding, current-jitter alpha sampling, and edge handling. Both existing input-preparation shaders already retain the native scene alpha in their linear-color output; keep that current-frame input available and preserve its precision instead of importing the original game color again. Write directly into the shared scaled-scene destination. A native destination that cannot be shared needs one return copy from a shared encoded output. Signal completion only after encoding, then queue the D3D11 wait before native post-processing consumes the scene. This replaces the D3D11 encoder and final copy on the shared route, and removes the diagnostic identity pass.
6. Verify all three methods together, including saved Auto startup, Native/Auto changes, method/model switches, canceled scenes, cached-list replay, loading screens, resize, and resource retirement. Check exact input ownership and color/alpha conventions, SDK error reports, stable allocation counts, and GPU timing for preparation, reconstruction, return, and the complete frame. Record the same scene with matching probe settings before claiming a speedup.

`CopyResource` and `CopySubresourceRegion` are suitable for unchanged compatible data. They cannot evaluate the sRGB transfer function, rebuild motion, resample alpha, or resize the image. Shared handles expose one allocation to both APIs. A preparation shader can perform the needed conversion while writing that allocation, and the return shader can combine encoding with its final write. Move native-input preparation to D3D12 later if its game-owned inputs can be safely shared at creation. Keep any required copy at that boundary explicit. [D3D11 copy rules](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-copyresource), [shared resource import](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device-opensharedhandle)

The bridge experiments did not establish a worthwhile gain from extra queues, earlier signaling, explicit flushing, or alternate copy paths. Keep one direct queue, explicit states, and recording before submission. Compare the complete D3D12 reconstruction group against the current D3D11 group, including input preparation, output encoding, and total frame time. Shared fences preserve dependencies; they do not make the handoff free. Keep detailed experiment results in local analysis.

### Later custom passes

Group passes around their actual consumers. Connected D3D12 work can share private intermediates, but it must finish before native scattering, lighting, fog, or post-processing needs its result. Native shader replacements still run in D3D11 until their complete passes are moved. Start with equivalent algorithms and measure the complete group, including transfers and waits, before changing its implementation.

| Group | Initial boundary | Candidate improvements after the port |
| --- | --- | --- |
| Reconstruction | Prepared scene color, depth, and motion enter D3D12 before bloom; encoded output returns before native post-processing | One submission for SDK evaluation and output encoding; private SDK scratch and history; direct writes to the shared scene destination |
| Indirect lighting | Accepted geometry, materials, and lighting inputs enter before skin scattering; the composed result returns for native scattering | Keep depth reduction, tracing, temporal history, and spatial filtering together; evaluate wave reductions, tile classification, and compacted tracing work |
| Contact shadows | Accepted light/depth batches enter before their native lighting consumers | Preserve batched light work; evaluate wave operations within the depth scan while retaining workgroup synchronization where lanes cross wave boundaries |
| Ray/path tracing | Geometry, poses, materials, lights, and camera data enter at their verified producer boundaries; outputs return to their actual composition consumers | Keep acceleration structures, tracing, radiance caches, denoising or Ray Reconstruction, and their histories on D3D12; avoid exporting intermediate signals with no native consumer |

Select shader profiles from actual device, compiler, and runtime support. Evaluate wave operations and native 16-bit arithmetic inside the passes that benefit, preserving required synchronization and precision. A newer shader profile alone does not make an unchanged shader faster. Future tracing can evaluate shader execution reordering and opacity micromaps separately. Keep capability choices inside the backend and pass implementations.

Use another queue only when independent work can overlap profitably. Measure GPU contention and total frame time; keep the simpler schedule when results are indistinguishable. Share boundary images only. SDK scratch, denoising history, acceleration structures, and other D3D12-only data should stay private to D3D12.

For DLSS Frame Generation, identify a final post-processed/graded scene image without UI and retain its matching scene identity, motion, depth, and exposure information. Native 2D shaders also implement camera filters, so their presence alone cannot establish the HUD boundary. Verify the selected Streamline integration's D3D12 presentation path, UI handling, resource lifetimes, synchronization, and color encoding. Convert to PQ only if that SDK contract requires it. Frame generation remains planned work.
